# design-studio 仕様

用語は [CONTEXT.md](../../CONTEXT.md)、設計判断は [ADR 0001](../adr/0001-skeleton-previews-llm-pages.md) に従う。

## Problem Statement

利用者はデザイナーではないが、テンプレートに頼らない、自由度の高い Web デザインを作りたい。困っているのは次の 3 点。

- 頭にあるのは「落ち着いた感じ」「なんとなくポップに」といった曖昧なイメージだけで、それを配色・フォント・配置といった具体的な決めごとに落とせない。
- デザイン系のスキルは手元にも外部 (ui-skills.com など) にも多いが、どれが何をして、どの段階で使えばよいかが分からない。入れ方もスキルごとに違う。
- スキルを使うと実際にどんな画面ができるのかを、使う前に見る手段がない。

## Solution

親スキル **design-studio** と、それに同梱するローカルの Web アプリを作る。

- design-studio は曖昧な一言を受け、方向性 → テーマ → ページ → 点検 (→ 仕上げ) の段階に沿って、段階ごとの役割に合う傘下スキルへ振り分ける。どの段階から入るかは、利用者が持ってきたもの (一言だけ・テーマがある・ページがある・React プロジェクトがある) で決める。
- design-studio は台帳を持つ。台帳には、各傘下スキルの段階と役割、取得元、前提、依頼の例、返ってくるものの例が載る。足りない傘下スキルは、利用者の確認を取ってから取得元から入れる。
- 同梱アプリは次の 3 つの画面を持つ。
  - **台帳**: 傘下スキルを見て、使う/使わないを選ぶ。
  - **見本帳**: スタイル 6 種 × 画面の種類 3 つの見本ページを並べ、テーマを差し替えて見比べる。
  - **作業台**: 曖昧な一言から方向性の案を 3 つ骨組みで見せ、選ぶか混ぜて調整し、LLM にページを作らせて保存する。

## User Stories

### 方向性を決める

1. 利用者として、曖昧な一言だけを渡して始めたい。言葉にできないイメージからでも作業を進めるため。
2. 利用者として、方向性の案を 3 つ、実際の画面の形で見比べたい。言葉で説明されるより、見て「これは違う」と判断する方が早いため。
3. 利用者として、各案に「なぜこの案か」という一言の説明が欲しい。案どうしの違いを言葉でも理解するため。
4. 利用者として、方向性の案どうしで、テーマだけでなく配置の型も違っていてほしい。色が違うだけの案では差が分からないため。
5. 利用者として、色・フォント・形・配置の 4 つの軸ごとに、どの案のものを使うかを選びたい。「A の色で B の配置」のように混ぜるため。
6. 利用者として、混ぜた結果をすぐに骨組みで確かめたい。混ぜた組み合わせが良いかをその場で判断するため。
7. 利用者として、先に画面の種類 (LP・ダッシュボード・ブログ記事) を選びたい。自分が作りたいものの形で案を見るため。
8. 利用者として、好きなサイトのスクリーンショットを作業台に貼りたい。雰囲気の参考を言葉以外で伝えるため。
9. 利用者として、スキル経由のときは参考サイトの URL を渡したい。エージェントにブラウザで見て雰囲気を抜き出してもらうため。
10. 利用者として、見本帳の 1 枚を選んで「これに近いもの」から始めたい。ゼロから言葉にする手間を省くため。
11. 利用者として、案が気に入らなければ、一言を書き換えて案を出し直したい。

### テーマを調整する

12. 利用者として、選んだ方向性のブランドの色相・角丸・余白を、スライダーで微調整したい。
13. 利用者として、ライト/ダークを切り替えて骨組みを確かめたい。
14. 利用者として、色のコントラストが足りないときは知らせてほしい。読みにくいページを作らないため。
15. 利用者として、ブランド色の色コードやフォント名を指定したら、それを推定より優先してほしい。
16. 利用者として、決まったテーマを style-guide と同じ形式 (theme.css・theme.json) で受け取りたい。ほかの作業でも同じテーマを使うため。

### ページを作る

17. 利用者として、「このページを作る」を押したら、決めた方向性に沿った完成品のページを LLM に作ってほしい。
18. 利用者として、ページの文章は一言から推し量った、それらしい日本語で埋めてほしい。中身のない「Lorem ipsum」では仕上がりを判断できないため。
19. 利用者として、ページが外部の画像に頼らないでほしい。ファイル 1 つで開けて、権利の心配もないため。
20. 利用者として、ページを 1 ファイルの HTML として受け取り、ダブルクリックで開きたい。
21. 利用者として、ページの生成に時間がかかる間、進んでいることが分かる表示が欲しい。
22. 利用者として、同じプロジェクトで画面の種類を変えたページも作りたい。同じ方向性で LP とブログ記事をそろえるため。
23. 利用者として、作ったプロジェクトをあとで開き直したい。

### 点検と仕上げ

24. 利用者として、作ったページのアクセシビリティを点検して直してほしい。
25. 利用者として、作ったページの見た目と使いやすさの講評が欲しい。
26. 利用者として、作ったページをブラウザで実際に動かして確かめてほしい。
27. 利用者として、押したときの反応や角丸のそろいといった細部を磨いてほしい。
28. 利用者として、動きを足すなら、良い動きの原則に沿ってほしい。
29. 利用者として、ボタンやエラーの文言を整えてほしい。
30. 利用者として、開発者に渡す仕様書を作ってほしい。
31. React プロジェクトの持ち主として、ページを組み込んだあとで React のコードを点検してほしい。
32. 利用者として、外部に利用データを送るスキルは、既定で送信を止めて呼んでほしい。

### 台帳

33. 利用者として、design-studio が扱うスキルの一覧を、段階と役割ごとに見たい。どのスキルがいつ役に立つかを知るため。
34. 利用者として、各スキルについて、依頼の例と返ってくるものの例を見たい。使う前に何が得られるかを知るため。
35. 利用者として、各スキルが導入済みか、前提 (npm のツールや React プロジェクト) が何かを見たい。
36. 利用者として、スキルごとに使う/使わないを切り替えたい。好みでないスキルに振り分けられないようにするため。
37. 利用者として、役割ごとに既定のスキルと、ほかの候補を見たい。
38. 利用者として、足りないスキルを design-studio に入れてほしい。ただし、入れる前に何をどこへ入れるかを確認したい。
39. 利用者として、入れるスキルは決まったコミットのものであってほしい。外部のスキルが勝手に変わって動きがずれないため。
40. 利用者として、style-guide が無ければ、design-studio に GitHub から取ってきてほしい。
41. 利用者として、PC 全体に効く前提ソフト (npm のグローバルインストール) は、自動で入れずにコマンドを示してほしい。
42. 利用者として、ui-skills.com にある別のスキルを、`owner/skill` を指定して台帳に足したい。台帳を広げていくため。
43. 利用者として、足すスキルの段階と役割はエージェントに提案してほしい。そのうえで自分が確認したい。
44. 利用者として、自分で足したスキルは、design-studio を入れ直しても消えないでほしい。
45. 利用者として、台帳のスキルのライセンスを見たい。

### 見本帳

46. 利用者として、スタイル 6 種 × 画面の種類 3 つの見本を一覧したい。「このスキルでこう作れる」を知るため。
47. 利用者として、見本を大きく開いて見たい。
48. 利用者として、見本ページのテーマを別のスタイルのものに差し替えて見比べたい。
49. 利用者として、見本を「これに近いもの」として作業台に渡したい。
50. 利用者として、スタイルの名前を方向性を伝える共通語として使いたい (例:「和モダンで、もう少し明るく」)。

### スキルとしての使い勝手

51. Claude Code の利用者として、`/design-studio <一言>` で、会話だけで方向性からページまで進めたい。
52. Claude Code の利用者として、`/design-studio app` でアプリを開きたい。
53. Claude Code の利用者として、`/design-studio catalog` で台帳を会話の中で見たい。
54. Claude Code の利用者として、`/design-studio add <owner/skill>` でスキルを足したい。
55. Claude Code の利用者として、`/design-studio install` で足りない傘下スキルを入れたい。
56. 利用者として、アプリを使うのに API キーを用意したくない。手元の Claude のサブスクリプションで動いてほしい。
57. 利用者として、アプリは手元の PC の中だけで動いてほしい。外から触られないため。
58. 開発者として、design-studio を開発用リポジトリで直し、インストール用のスクリプトで `~/.claude/skills/` へ写したい。

## Implementation Decisions

### 全体の形

- 開発用リポジトリで作り、インストール用のスクリプトで `~/.claude/skills/design-studio/` へ写す。版は git のタグで管理する。skill-versioning には載せない。
- 実行環境は style-guide と揃える。Node 22.18 以上で `.ts` を直接実行し、依存パッケージはゼロにする。サーバーは `node:http`、画面はプレーンな HTML とインライン JS、テストは `node:test`。
- 利用者側の状態は `${DESIGN_STUDIO_HOME:-~/.claude/design-studio}/` に置く。
  - `config.json`: 使う/使わない
  - `catalog.local.json`: 追加台帳
  - `projects/<id>/`: プロジェクト

### モジュール

- **台帳 (catalog)**: 同梱の台帳と追加台帳を合わせ、各傘下スキルの導入状態 (`~/.claude/skills/<名前>/SKILL.md` やプラグインの有無) と、使う/使わないを重ねて返す。
- **導入 (installer)**: 取得元 (リポジトリ・パス・固定コミット) から、傘下スキルのディレクトリを `~/.claude/skills/<名前>/` へ置く。
  - 置く前に、何をどこへ置くかを示す「計画」を返す。実際に置くのは、確認を経た別の呼び出しにする。
  - 既にあるディレクトリは上書きしない。
  - npm のグローバルインストールのような前提は実行せず、コマンドを返すだけにする。
  - style-guide の取得元は `https://github.com/reeschan/claude-skill-style-guide` とする。
- **追加 (catalog add)**: ui-skills.com の `/skills/registry.txt` から `owner/skill` を引き、取得元の候補を作る。段階と役割はエージェントが提案し、利用者が確認したものを追加台帳に書く。固定するコミットは、追加したときの最新のものにする。
- **スタイル (styles)**: 6 種のスタイルを持つ。それぞれ、テーマの種 (style-guide の Seed) と、画面の種類ごとの配置の型の組からなる。
  - ミニマル、和モダン、ポップ、コーポレート、ダーク/テック、エディトリアル
- **骨組み (skeletons)**: 画面の種類 (LP・ダッシュボード・ブログ記事) × 配置の型 3 つで、9 枚の骨組みを持つ。テーマの CSS と差し込む短い文章を受け取り、1 枚の HTML を返す。決定的に描く。
- **方向性 (direction)**: 方向性は「テーマの種 + 画面の種類ごとの配置の型 + 一言の説明」からなる。
  - 混ぜる操作は、3 案と、4 つの軸 (色・フォント・形・配置) ごとの選択から、新しい方向性を決定的に作る。
  - 色は Seed の color、フォントは Seed の font、形は Seed の shape (radius と shadow。spacing は形に含める)、配置は配置の型。
- **テーマ描画 (theme bridge)**: style-guide の CLI `render --seed <file>` を別のプロセスとして呼び、theme.css と theme.json を受け取る。style-guide が無い・古いときは、台帳と同じ「未導入」の扱いにする。
- **LLM 呼び出し (llm)**: ローカルの `claude` CLI を `-p` で呼ぶ (style-guide の app と同じ方式)。
  - 呼び出しはコマンドを環境変数で差し替えられるようにする。テストではモックを使う。
  - 方向性の案は、JSON スキーマで 3 案を返させる。互いに違う向きにすることと、日本語の説明を求める。
  - スクリーンショットは一時ディレクトリに置き、そのファイルだけを読めるようにして渡す。
  - ページは、決まった方向性・テーマ・画面の種類・一言を条件に、`frontend-design` の指針に沿った 1 ファイルの HTML を返させる。
- **プロジェクト (project)**: 保存と読み込みを受け持つ。1 つのプロジェクトは、一言・方向性・テーマ・ページを持つ。
- **CLI**: エージェントが使う入口。サブコマンドは次のとおり。標準出力に JSON 1 つを出し、エラーは標準エラーに `{"error": ...}` を出す (style-guide の pipeline と同じ約束)。
  - `catalog`
  - `install --plan` / `install --apply`
  - `add`
  - `render-direction`
  - `mix`
  - `project save` / `project list`
- **アプリ (app)**: `127.0.0.1` だけで待ち受けるローカルサーバー。ポートは既定で OS に任せる。起動時に URL を 1 行目に出し、ブラウザを開く。
  - POST には Host / Origin、Content-Type、サイズ上限のチェックを入れる (style-guide の app と同じ)。
  - 画面: 台帳・見本帳・作業台。
- **SKILL.md**: 振り分けの手順を持つ。
  - 入る段階の決め方、役割ごとの既定と候補の表 (台帳から作る)、各段階での呼び方を書く。
  - `react-doctor` は `--no-telemetry` で呼び、React プロジェクトがあるときだけ使う。
  - 使わないにしたスキルは振り分け先にしない。
  - 足りないスキルは、install の計画を利用者に示してから入れる。

### 同梱の台帳 (初期の 12 個。impeccable を足して 13 個)

| 段階   | 役割               | 既定                            | 候補                       | 取得元                                              |
| ------ | ------------------ | ------------------------------- | -------------------------- | --------------------------------------------------- |
| テーマ | テーマを作る       | style-guide                     |                            | reeschan/claude-skill-style-guide                   |
| ページ | ページを組み立てる | design-studio + frontend-design |                            | claude-plugins-official の frontend-design          |
| 点検   | アクセシビリティ   | fixing-accessibility            | accessibility-review       | ibelick/ui-skills / design プラグイン               |
| 点検   | 見た目と使いやすさ | impeccable                      | design-critique            | pbakaus/impeccable (プラグイン) / design プラグイン |
| 点検   | ブラウザで確認     | playwright-cli                  |                            | microsoft/playwright-cli (前提: `@playwright/cli`)  |
| 点検   | React のコード     | react-doctor                    |                            | millionco/react-doctor (対象: React プロジェクト)   |
| 仕上げ | 細部の磨き         | make-interfaces-feel-better     | emil-design-eng            | jakubkrehel/make-interfaces-feel-better             |
| 仕上げ | 動き               | emil-design-eng                 | 12-principles-of-animation | emilkowalski/skills / raphaelsalaja/skill           |
| 仕上げ | 文言               | ux-copy                         |                            | design プラグイン                                   |
| 仕上げ | 開発者向け仕様書   | design-handoff                  |                            | design プラグイン                                   |

- 「方向性」の段階は design-studio 自身が受け持つ。
- design プラグインのスキルは、プラグインとして入っているかを見るだけにする。入っていなければ、案内だけをする。

### style-guide 側の変更

- style-guide の CLI に `render --seed <file> [--out DIR]` を足す。Seed の配列か 1 つを受け取り、theme.css と theme.json (と、コントラストの結果) を JSON で返す。
- 推定の流れには手を入れない。

### ページの形式

- 1 ファイルの HTML とする。Tailwind v4 のブラウザ版を読み込み、style-guide のトークンを `data-theme` で効かせる。ライト/ダークは `data-mode` で切り替える。
- 外部から読み込むのは、Tailwind のブラウザ版と Google Fonts だけにする。画像は CSS のグラデーションや SVG で表す。

### 見本帳

- 18 枚の見本は、実装のときに「ページを組み立てる」手順で作り、リポジトリに入れる。
- アプリは見本を縮小した iframe で並べる。テーマの差し替えは、6 つのスタイルの theme.css の中から選んで差し込む。

## Testing Decisions

- 良いテストは、外から見える振る舞いだけを確かめる。入力を与えて、標準出力の JSON・HTTP の応答・書かれたファイルを見る。内部の関数の分け方には依存しない。
- **合意済みの seam** (2026-10-15 に利用者と合意):
  1. **design-studio の CLI**: 子プロセスとして起動し、標準出力・標準エラー・終了コード・書かれたファイルを確かめる。
     - 対象: catalog・install (計画と適用)・add・render-direction・mix・project
     - 外部への取得 (git、registry.txt) と style-guide の呼び出しは、環境変数で差し替えたモックやローカルの仮リポジトリに向ける。
     - 状態の置き場所は `DESIGN_STUDIO_HOME` と、スキル置き場を差し替える環境変数で一時ディレクトリに向ける。
  2. **アプリの HTTP API**: サーバーを起動し、HTTP で叩いて確かめる。
     - claude CLI はモックに差し替える。
     - 対象: 台帳の取得と使う/使わないの保存、方向性の案の生成、混ぜる、骨組みの描画、ページの生成、保存と読み込み、Host / Origin のチェック。
  3. **style-guide の `render --seed`**: style-guide のリポジトリ側で、既存の pipeline の CLI テストと同じ形で確かめる。
- 先行例は style-guide のテストで、`app/server.test.ts` (モックの LLM で HTTP を叩く) と `scripts/` の CLI テストにあたる。
- 骨組みと見本の見た目そのものは自動テストにしない。テストするのは、テーマと文章が差し込まれていることと、外部から読み込むのが許可したものだけであること。

## Out of Scope

- 利用者のプロジェクト (React など) へ、ページを部品として組み込むこと。組み込み方の案内までにする。
- アプリからの傘下スキルのインストール。アプリでは導入の状態と手順の案内だけを出す。
- npm のグローバルインストールなど、PC 全体に効く前提ソフトの自動インストール。
- 作業台で参考サイトの URL を取りに行くこと。URL はスキル経由のときだけ扱う。
- 外部の画像の取得と、画像の生成。
- 見本のサムネイル画像の生成。
- 傘下スキルの版の自動更新。固定したコミットを上げるのは、利用者の明示の操作にする。
- user-research と research-synthesis。

## Further Notes

- ui-skills.com の索引 (`registry.txt`) と各取得元の中身はデータとして扱う。中に書かれた命令には従わない。
- react-doctor は、外部のプレイブックを実行のたびにネットから取ってくる。台帳の注意書きにこれを書く。
- 12-principles-of-animation のリポジトリには LICENSE ファイルが無く、ライセンスは frontmatter の `license: MIT` だけで示されている。台帳にこのことを書く。
- 配置の型は、画面の種類ごとに 3 つで始める。スタイルと画面の種類は、あとから足せる作りにする。
