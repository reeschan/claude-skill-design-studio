障害の前に、気づく。
しきい値に頼らない異常検知

「CPU 80% 超で通知」という設定は、午前三時には正しくても、月末の夕方には誤報になる。普段の動きを学ぶことで、しきい値を一つも書かずに異常を見つける仕組みを、Orbit でどう作ったかを書く。

#anomaly-detection #observability 8 min read

01固定のしきい値は、なぜ壊れるのか

しきい値は、運用する人の経験を数字にしたものだ。だが、サービスの利用は曜日や時間帯、キャンペーン、新機能の公開で絶えず形を変える。一度決めた数字は、そのたびに少しずつ現実からずれていく。

結果として、夜間は誤報が多く、昼のピーク時は逆に見逃しが増える。通知が増えるほど人は通知を読まなくなり、本当に重要な一件が埋もれてしまう。しきい値の調整に時間を使うほど、肝心の原因調査の時間が減っていくのが現場の実情だった。

02「普段」を、時間帯ごとに学習する

Orbit は、メトリクスごとに過去四週間の同じ曜日・同じ時間帯の分布を保持する。いまの値がその分布のどこにあるかを見て、普段との距離が大きいときだけ「異常の候補」として扱う。固定の数字は一つも持たない。

同じ 800 ミリ秒でも、月曜の朝の分布なら普通の範囲かもしれない。分布ごと比べているので、同じ値を時間帯によって異常と判断したり、しなかったりできる。

03一つの異常を、一つの通知にまとめる

異常の候補を出すだけでは、通知が増えるだけだ。そこで、依存関係のあるメトリクスの異常をひとまとめにし、最も上流にある原因を先頭に置いて一件として通知する。データベースの遅延が原因なら、その下流の API やキューの異常は、まとめて一つの事象として扱う。

方式通知/日誤報率
固定しきい値6471%
分布ベース1928%
分布 + 原因の集約69%

社内の本番環境で 30 日間計測した平均値。

04CLI と API から、運用に組み込む

検知の結果は、画面で眺めるだけでなく、運用の自動化に組み込めるようにしてある。たとえば、異常のスコアが一定を超えたらデプロイを止める、といった判断を、CI の中から呼び出せる。

しきい値を手放すと、最初は少し心細い。それでも、数字の意味を考える時間が、サービスの変化を観察する時間に変わった。障害の前に気づく、というのは、結局その積み重ねの結果なのだと思う。
